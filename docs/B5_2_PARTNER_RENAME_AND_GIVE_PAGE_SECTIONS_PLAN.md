## 3. Design

### 3.1 Rename "Give" → "Partner" (display-layer only — zero migrations)

**Amendment (approved 2026-09-26):** a `SectionPage` label change would require a
choices-only `AlterField` migration; the approval requires **no migrations**, so
the label is aliased at the display layer instead — the model field, its choices,
the DB values, and the migration state are all untouched
(`makemigrations --check` stays clean).

| Touchpoint | Before | After (implemented) |
|---|---|---|
| Admin card name (`PAGE_SECTION_GROUPS`) | `('give', 'Give', 'GiveSections', 'content')` | `('give', 'Partner', 'GiveSections', 'content')` |
| Object display / breadcrumb (`__str__`) | "Give - M-Pesa Giving" | proxy `GiveSections.get_page_display()` returns **'Partner'** → "Partner - M-Pesa Giving" |
| Change-form readonly "Page" row | auto choices label "Give" | base-admin `page_label` readonly method → shows the proxy display: **"Partner"** (other pages unchanged: Home/About/Events/Visit/Sermons/Series/Prayer/Contact) |
| Code comment (`admin.py:142`) | "…Series, Give, Contact" | "…Series, Partner, Contact" |

**The internal key stays `'give'`** (decision D2): no data migration, no frontend
page-key change, URLs untouched, the frontend gate prefix stays `"give"`. Only
what humans read changes. **No migration file is created or needed.**

### 3.2 Partner page sections: 1 → 4

`content/sections_registry.py` — replace the single give tuple with:

```python
# --- Partner (page key: 'give') ---
(SectionPage.GIVE, 'page-hero', 'Page Hero'),
(SectionPage.GIVE, 'why-we-give', 'Why We Give'),
(SectionPage.GIVE, 'mpesa-giving', 'M-Pesa Giving'),
(SectionPage.GIVE, 'where-giving-goes', 'Where Your Giving Goes'),
```

`give.astro` — wrap the three currently ungated sections in the existing gate pattern:

```
{on("why-we-give") && ( <section class="register-celestial …">…</section> )}
{on("mpesa-giving") && ( <section class="register-parchment …">…</section> )}
{on("where-giving-goes") && ( <section class="register-celestial …">…</section> )}
```

- `ensure_registered()` auto-creates the 3 new rows (enabled) on the next registry touch (admin changelist or `/api/sections`) — **no manual DB step, no data migration**.
- The existing `page-hero` row and its toggle state are untouched.
- Nothing is deleted: disabling hides a section; re-enabling restores it in place.
- Registry total grows 28 → 31 keys; frontend gates 28 → 31 (give: 1 → 4).

## 7. Risks & mitigations

- **Non-destructive:** registry additions + label changes only; no row is deleted; the existing `page-hero` toggle survives untouched.
- Choices-only migration: no SQL executed (verified pattern from migration 0017).
- If decision D4 = "remove Page Hero from the list": the DB row would survive (registry never deletes) and would keep appearing as a dead toggle in the admin — true removal would require deleting the row. **Recommendation: keep it** (the hero is a genuine page section).
- Gating section ③ (M-Pesa card) removes the till details from the page when disabled — that is the intended admin power; the row/till data is never deleted.
